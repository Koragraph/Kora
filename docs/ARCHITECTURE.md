# Kora architecture

What runs, how the packages depend on each other, how a chat turn and an index move through the system, and where every
byte Kora keeps on disk lives. How the code graph works end to end (store, ingest, freshness, injection, the chip) is in
[`docs/graph/HOW-IT-WORKS.md`](graph/HOW-IT-WORKS.md) and is not repeated here.

## Processes

```
Kora.app (Electron)                    kora daemon  (`kora server run`, node --liftoff-only, detached, outlives the app)
  main   apps/desktop/src/main.ts        unix socket <KORA_HOME>/kora.sock  ── CLI, hooks, fleet workers, MCP bridges
  preload / renderer = apps/web          ui-server (packages/ui-server, bundled to runtime/ui/ui-server.cjs, loaded
        │  kora:// serves the web build    in-process by runtime/src/server/ui.ts) on 127.0.0.1:<port>  /ws + /api/*
        └── ws + bearer UI token ────────▶ Runtime (panes, worktrees, fleet, swarm, merge) + SessionManager (chat lanes)
                                          ├─ worker_threads: graph query pool (graph/offload.ts → graph/worker.ts),
                                          │                  blob memory (blobs/memory-host.ts → memory-worker.ts)
                                          ├─ child processes: `kora ingest` / engine catch-up (--liftoff-only), merge
                                          │   gates, git, the housekeeping WAL checkpoint, agent CLIs in node-pty panes
                                          └─ agent SDK sessions: Claude (Agent SDK), Codex (`codex exec --json`), Antigravity (`agy --print`
                                              stream-json, one child per turn), OpenCode
kora CLI (~/.local/bin/kora → <KORA_HOME>/app/bin/{node,kora.js}): short-lived, talks to the daemon over the socket
hooks (`node ${KORA_BIN:-…/kora.js} hook <event>` in a repo's .claude/settings.local.json): short-lived per event
```

- **Desktop** (`apps/desktop`): Electron main + preloads. On launch runs `Contents/Resources/kora-runtime.sh ensure`
  (`ShellKoraRuntime.ts`): copies the bundle's runtime to `<KORA_HOME>/app` when the build differs, writes the CLI shim,
  starts the daemon if down. It never owns chat state; it attaches to the daemon after `/.well-known/kora/identity`
  proves the daemon holds the UI token (`client-runtime/src/auth/identity.ts`).
- **Daemon** (`packages/runtime/src/server/daemon.ts`): one per flavor per machine. Serves the socket protocol
  (`protocol/types.ts` methods) and hosts the ui-server. Heavy graph work stays off its event loop (worker threads,
  child processes); `startStallDetector` logs every stall. `startHousekeeping` (server/housekeeping.ts) runs at start
  and hourly.
- **ui-server** (`packages/ui-server`): the Effect RpcServer the web client speaks (`KoraRpcGroup` in contracts). It
  sees the daemon only through the structural `UiHost` slice (`ui-server/src/host.ts`, built in
  `runtime/src/server/ui.ts`), never by importing runtime source. It projects `ChatEvent`s into the client's thread
  read models and serves `/api/graph*` from the graph store (read-only, through the daemon's better-sqlite3 opener).
- **Hooks / CLI / MCP bridges** (`runtime/src/cli`): fresh processes that dial the socket; when the daemon is down,
  graph calls fall back in-process.
- **Workers**: agent CLIs (OpenCode, Claude, Codex, …) spawned by `kora_spawn` as node-pty panes, usually in their own
  worktree under `<KORA_HOME>/worktrees`.
- **Graph engine** (`packages/runtime/koragraph`, vendored; edits only per `koragraph/PATCHES.md`): loaded in-process by
  the daemon, its worker threads and the CLI; ingest and catch-up run as separate processes.

## Packages and layering

```
apps/web ──▶ client-runtime ──▶ shared ──▶ contracts        (contracts: Effect Schema only, no node:, no I/O)
apps/desktop ──▶ contracts, shared, client-runtime (one import)
packages/ui-server ──▶ contracts, shared   (+ runtime/package.json for the version; the daemon is reached via UiHost)
packages/runtime: plain tsc CommonJS, no @kora/* imports; bundles ui-server as runtime/ui/ui-server.cjs
```

No cross-package cycles; web imports only contracts / shared / client-runtime; desktop does not
import web (its `src/web/` is its own webview code); contracts imports only `effect`. Known mirrored code, each kept in
step by comment rather than shared: the index-root policy (`runtime/graph/embedded.ts` `unsafeIndexRoot` ↔
`ui-server/graph.ts` `isSafeToIndex`/`SYSTEM_ROOTS`/`tempOrVolumeRoot`), blob folders (`runtime/blobs/home.ts` ↔
`ui-server/assistantFs.ts`), and the home/store resolvers (`runtime/protocol/types.ts koraHome` ↔
`ui-server/paths.ts` ↔ `desktop/app/ShellFlavor.ts` + `ShellStatePaths.ts` ↔ `kora-runtime.sh` ↔
`cli/commands/uninstall.ts uninstallPaths`).

## A chat turn

1. Web composer → `orchestration.dispatchCommand` over `/ws` → ui-server `kora-chat.ts` (`ChatEngine`).
2. The engine maps the client thread to a runtime session and calls `SessionManager.sendTurn` through `UiHost`
   (`runtime/src/session/session-manager.ts`). Trust is consulted first (`runtime/src/trust/gate.ts`).
3. The driver (`session/drivers/claude-driver.ts`, `codex-driver.ts`, `antigravity-driver.ts`, `opencode-driver.ts`) runs
   the turn. Before sending, the Claude/Codex/Antigravity drivers prepend the graph's resolved declarations (`graph/prompt-inject.ts`; the repo's
   prompt hook stands down because `KORA_INJECT_OWNER=driver`), and `freshenIndex` starts a catch-up ingest if the
   index is behind HEAD. Each injection appends a row to `<KORA_HOME>/inject.jsonl`.
4. Driver output becomes `ChatEvent`s, appended to `<KORA_HOME>/chat/<thread>/events.ndjson` (`session/store.ts`, the
   source of truth), and streamed to the ui-server, which projects them into `<KORA_HOME>/kora-daemon/threads/` and
   pushes `ThreadEvent`s to subscribed clients (every wire value through `toJsonValue`).
5. Delegation: the lead calls `kora_spawn` (session/fleet-tools.ts) → the user approves picks (`worker-picker.ts`) →
   `Runtime.spawnPane` starts a worker in a worktree; `kora_wait` returns its report. Merges run the graph-verified gate
   in a child (`runtime/src/merge`).

## Indexing

The chip's "Index this repo", `kora ingest`, a stale index on the next code prompt, or a worker pane's background index
all end in a `kora ingest <root>` child process (`--liftoff-only`) that writes the store through the engine. Every path
refuses unsafe roots with `unsafeIndexRoot`. Queries go through the daemon's graph worker pool; the chip reads
`/api/graph/status` (ui-server `graph.ts`). Details, freshness and failure modes: `docs/graph/HOW-IT-WORKS.md`.

## Storage map

Paths are for stable; Kora Dev is the same under `~/.kora-dev` unless stated. **Kind**: D = derived / rebuildable,
U = user data, S = secret, C = config, L = log/telemetry. **Uninstall**: `—` = kept by plain `kora uninstall`;
`purge` = deleted by `--purge --yes` (whole `KORA_HOME`, graph home and Electron user data); `plain` = removed by
plain uninstall too. `KORA_HOME` is created and kept 0700 by the daemon (`privateDir`), so everything under it is
owner-only whatever its own mode.
